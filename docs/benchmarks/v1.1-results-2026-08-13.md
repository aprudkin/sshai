# sshai v1.1 benchmark results — 2026-08-13

**Task:** [aimem#735](https://github.com/aprudkin/aimem/issues/735)

**Decision:** needs work. `sshai` reduced agent-visible tool output by 99.86% and total Codex input
tokens by 44.71%, while matching the raw-SSH observation success rate. Four of five v1.1 targets
passed, but the primary target of at least 80% input-token reduction did not.

## Frozen run

- Protocol: [v1.1 protocol](v1.1-protocol.md), version 2.
- Manifest: [v1.1 manifest v2](v1.1-manifest-v2.json), committed before the measured pair.
- Codex: 0.147.0, `gpt-5.6-sol`, high reasoning effort, fresh sessions.
- Targets: two Linux/bash SSH aliases and one Windows/PowerShell 7.6.3 alias.
- Scenario: 36 read-only observations, including one approximately 10 MB and two approximately
  1 MB synthetic producers, repeated 2,000-line checks, intentional exit 7, and post-failure
  health checks.
- Order: raw SSH, then `sshai`; 180-second per-call watchdog in both branches.

An earlier protocol-v1 raw pilot was stopped before Windows after its second 10 MB producer
remained active for more than 15 minutes. No valid `sshai` pair existed, so none of the pilot data
is included below. Protocol v2 and a new artifact directory were frozen before restarting both
branches.

## Failures and boundaries

The two branches both succeeded on 34 observations, but not on the same two:

- raw SSH: one Linux command produced its expected filesystem summary and then the remote side
  closed the connection, so the local exit was 255; Windows direct PowerShell stdin printed the
  intentional failure but translated remote `exit 7` to local exit 1;
- `sshai`: the first two Linux calls returned `transport-error=ssh` immediately; the same branch
  recovered without an agent retry, and all later calls on that host passed, including the 10 MB
  producer and honest exit 7 on all three hosts.

This differing failure set is a branch-order/network confounder. It supports only the stated
equality of observed success rates, not a claim that either transport is more reliable from this
single sample.

Raw tool responses for the 10 MB Linux and approximately 1 MB Windows producers plateaued at
1,048,607 and 1,048,605 bytes. There was no explicit truncation marker in the Codex JSONL. This is
evidence of an agent-tool response floor around 1 MiB, not proof that full raw output reached the
model. The reported 99.86% output reduction is therefore conservative with respect to the remote
producer, but exact for the bytes visible in the JSONL.

Token estimates for tool output use `ceil(UTF-8 bytes / 4)`; they are not model-tokenizer counts.
The input-token figures are the actual final `turn.completed.usage` counters. No no-op control was
subtracted: constant system/project instructions, the branch prompt, reasoning, and accumulated
context remain part of both measured totals. The result explains why a 99.86% reduction in visible
tool bytes becomes only 44.71% at the full-session input-token level.

Both persisted Codex rollouts were independently scanned for event/item types containing
`compact`; neither contained one. This verifies the JSONL observation for these sessions, within
the event schema exposed by Codex 0.147.0.

## Recommended next step

Treat bounded output as validated and the 80% whole-session claim as unvalidated. The next
iteration should reduce agent-visible call count as well as output size: define a protocol where
`sshai` fan-out can satisfy multiple host observations in one agent call, and add a paired no-op
control with the same number of model decisions before interpreting marginal input-token savings.
Separately investigate the two initial `transport-error=ssh` results before making a reliability
claim. Do not move to unrelated v2 features on the strength of this sample.
