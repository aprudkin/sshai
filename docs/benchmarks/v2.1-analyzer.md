# sshai fan-out benchmark analyzer definition v2.1 amendment 2

**Task:** [aimem#743](https://github.com/aprudkin/aimem/issues/743)

**Analyzer schema:** `sshai-benchmark-analysis/v2.1-amendment-2`

**Status:** approved implementation candidate; not yet frozen for measurement

The base v2.1 analyzer remains the historical consumer for the completed three-replicate result.
Amendment 1 remains the historical consumer for its immutable invalid root. Amendment 2 applies
only to a new eight-replicate manifest and artifact root.

This file is the normative definition for the amended result consumer. A report is not valid
merely because the analyzer exits successfully; every input, population, provenance, and coverage
gate below must pass. The unchanged within-branch artifacts retain their v2.1 schemas; only the
study-level manifest and analysis schema carry `v2.1-amendment-2`.

## Inputs

For each of eight replicates the analyzer consumes:

- one frozen manifest;
- four complete Codex-exec JSONL files: `raw-control`, `raw`, `fanout-control`, and `fanout`;
- four run metadata files containing process exit, elapsed time, and stderr coverage;
- four persisted Codex rollout JSONL files independently resolved from the observed thread IDs;
- SHA-256 digests for every input.

The analyzer rejects missing, overwritten, duplicate, truncated, malformed, or cross-replicate
inputs. Each Codex-exec file must contain exactly one `thread.started`, one `turn.started`, one
`turn.completed`, and a final usage object. Its thread ID must equal the persisted rollout's
session identity.

## Marker grammar

A planned command prefixes its executable invocation with both environment assignments:

```text
BENCH_V21_CALL=<branch>:<call-id> BENCH_V21_OBS=<obs-id>[,<obs-id>...] <executable> ...
```

`branch` is one of `raw-control`, `raw`, `fanout-control`, or `fanout`. `call-id` is unique within
the branch. Observation IDs are exactly `L01` through `L24` and `W01` through `W12`, in manifest
order, with no whitespace or duplicates. Because the assignments are part of the invocation rather
than shell comments, removing comments cannot remove call identity. The analyzer matches this
grammar only in the completed command's command field; output or message text cannot create a
marker.

The manifest maps every call ID to its exact ordered observation list. A marker that differs from
that mapping invalidates the branch.

One completed `command_execution` item may contain exactly one marker match. Two otherwise valid
markers in one item prove that multiple displayed fences were batched into one agent-visible call
and invalidate the branch before call or observation evidence is credited. Multiple command items
with the same call ID remain a separate duplicate-call violation.

## Populations

| Name | Definition | Consumers |
|---|---|---|
| all command calls | every `item.completed` whose item type is exactly `command_execution` | diagnostic count and all-call output summary only |
| marked command calls | all command calls with one valid manifest-declared marker | call count, retries, tool-output sum/p95/max, call reduction, acceptance |
| unmarked command calls | all command calls without a valid marker | published separately; never accepted as workload evidence |
| declared observations | the 36 manifest observation IDs assigned by valid marked calls | coverage, per-host outcome, success rate |
| lifecycle records | exact allowed record types below | compaction count and coverage validity |

Nearest-rank p95 is computed over the marked command-call population. The estimated token count
for one tool response is `ceil(len(UTF-8 bytes) / 4)`. The analyzer also reports all-call output
statistics, but no acceptance consumer may read them.

Observation success requires a valid declared call plus host-specific evidence matching the
manifest's host and expected remote exit. A successful shell exit without every declared fan-out
result is incomplete, not successful.

## Lifecycle records

The allowed explicit compaction record is top-level `type=compacted`. In Codex-exec output it is
counted only when that exact top-level type is present. In persisted rollouts it is counted only
when the record's exact top-level type is `compacted`.

No substring search is permitted. `compact` or `compaction` inside agent messages, reasoning,
commands, command output, nested payload message text, or unrelated event/item types counts zero.
An unrecognized top-level lifecycle-like type is schema drift: preserve it, report the type name,
and invalidate the replicate instead of guessing its meaning.

For every branch the report contains:

```json
{
  "compactions": {
    "codex_exec": 0,
    "persisted_rollout": 0,
    "matched": true
  }
}
```

`matched=false`, a missing persisted rollout, or a thread-identity mismatch invalidates the
replicate.

## Input-token and control equations

For each usage field `u` (`input_tokens`, `cached_input_tokens`, and derived non-cached input):

```text
raw_margin(u)    = raw(u)    - raw_control(u)
fanout_margin(u) = fanout(u) - fanout_control(u)
```

Raw totals and both signed marginals are always published. The reduction is defined only when
`raw_margin(input_tokens) > 0` and `fanout_margin(input_tokens) > 0`:

```text
control_adjusted_reduction =
  (raw_margin(input_tokens) - fanout_margin(input_tokens)) / raw_margin(input_tokens)
```

If either workload marginal is non-positive, emit its signed value and the label
`indistinguishable-from-control-floor`. Do not clamp it to zero, divide by it, or report a saving
above 100%. The amended sampling gate, rather than any single floor pair, determines whether the
fixed study remains interpretable.

Across the eight valid replicates, each pair whose raw and fan-out workload marginals are both
positive contributes one defined control-adjusted reduction. A non-positive marginal remains a
published `indistinguishable-from-control-floor` pair and contributes no numeric reduction. The
decision consumer uses the median of defined reductions only when at least six are defined and no
more than two pairs are at the control floor. It does not pool token counters across sessions.

The manifest freezes two repetitions of the exact four-order cycle defined by the protocol. The
analyzer rejects a missing, additional, reordered, or replacement replicate; it does not stop
early after a favorable prefix.

## Validity gates

Before computing a comparative decision, require:

1. manifest schema and frozen flag match `v2.1-amendment-2`, including eight replicates, the exact
   balanced branch schedule, minimum six defined reductions, maximum two control-floor pairs, and
   the 80% median threshold;
2. all recorded file digests match current input bytes;
3. executable path, SHA-256, source revision, `vcs.modified=false`, and smoke result match the
   frozen preflight;
4. model, reasoning effort, Codex version, prompt/helper digests, timeout 180, and artifact paths
   match the manifest;
5. branch process exits and JSONL coverage are complete, and run metadata branch row/index match
   the manifest schedule;
6. marked-call counts are 36, 36, 24, and 24 in manifest order;
7. each control contains no remote command and each workload call uses only its declared target;
8. both workload branches cover the same 36 observation IDs exactly once;
9. Codex-exec and persisted lifecycle counts match for every branch;
10. the analyzer revision and definition digest match the manifest.

Any failed gate yields `valid=false`, records exact reasons, and suppresses `confirmed` or
`needs-work`. Measurements remain visible as evidence about the failed probe but are not promoted
to comparative results. A readable frozen manifest therefore produces an analysis document even
when branch inputs are invalid; that document retains bounded path, byte-count, and SHA-256
evidence for every available branch artifact. Process failure is reserved for an unreadable or
invalid manifest or failure to publish the requested output document.

## Amended decision outcomes

After all eight replicates pass validity and population gates:

- `inconclusive` if fewer than six input-token reductions are defined or more than two pairs are
  labelled `indistinguishable-from-control-floor`;
- `confirmed` if the sampling gate passes, every other acceptance gate passes, and the median of
  the defined input-token reductions is at least 80%;
- `needs-work` if the sampling gate passes but the median or another acceptance target fails.

The report always publishes the fixed replicate count, defined-reduction count, control-floor
count, signed marginals, and every per-replicate status. It never imputes a floor pair, clamps a
margin to zero, or replaces a floor pair with a new run.

## Required negative controls

The focused analyzer tests must demonstrate all of these before measurement:

- two large unmarked setup calls can change all-call p95 without changing marked p95 or its
  acceptance target;
- marker-looking text in output or agent prose cannot create a planned call or observation;
- `compact`, `compaction`, and `truncated` in prose count as zero lifecycle events;
- exactly one top-level `type=compacted` record counts as one in both source formats;
- differing Codex-exec and persisted counts produce `matched=false` and invalidate coverage;
- duplicate, missing, malformed, or unexpected call/observation markers fail closed;
- two valid fence markers concatenated into one command item fail closed even when its exit is zero;
- non-positive workload marginals produce `indistinguishable-from-control-floor`, never a
  percentage above 100%;
- six defined reductions plus two control-floor pairs can satisfy the sampling gate, while five
  defined reductions plus three control-floor pairs must be `inconclusive`;
- a complete eight-defined sample below the 80% median threshold is `needs-work`.

`scripts/test_benchmark_v1_1.py` preserves the historical population-mismatch regression.
`scripts/test_benchmark_v2_1.py` covers every boundary above against the executable amended
analyzer helpers. Both test files must pass before the runner is allowed to start a measured
branch.
